1 Теоретическое обоснование разрабатываемого программного продукта

1.1 Анализ предметной области
На современном этапе цифровой трансформации образовательные и административные организации активно переходят к централизованному управлению жизненным циклом компьютерной техники [1], [2]. Значительный объем оборудования, различный уровень износа, необходимость оперативного ремонта и регулярного планового обслуживания формируют устойчивую потребность в автоматизации процессов учета и сопровождения технической инфраструктуры [3].

Практика эксплуатации показывает, что ведение сведений о состоянии оборудования в разрозненных таблицах и локальных документах приводит к задержкам в обработке заявок, росту числа просроченных регламентных работ и недостаточной прозрачности расходов запасных частей [4], [5]. В результате руководство организации не получает своевременной и полной картины: какие единицы техники требуют первоочередного вмешательства, какие заявки находятся в критической стадии, какие складские позиции приближаются к дефициту [6].

Предметная область разрабатываемой системы включает следующие ключевые процессы:
- учет оборудования и его эксплуатационных характеристик;
- регистрация неисправностей и формирование заявок на ремонт;
- управление статусами выполнения ремонтных работ;
- планирование и контроль выполнения технического обслуживания;
- учет запасных частей и контроль минимальных остатков;
- формирование отчетности для анализа состояния процессов эксплуатации [7], [8].

Основными пользователями системы являются:
- администратор - управление доступом, контроль целостности данных, сопровождение системы;
- аналитик - формирование отчетов, анализ статистики ремонтов и обслуживания;
- оператор - ежедневная регистрация, обработка и сопровождение заявок.

Для рассматриваемой предметной области критически важны следующие требования:
- надежная аутентификация и разграничение прав доступа [9];
- целостность данных при параллельной работе пользователей [10];
- трассируемость действий через аудит изменений [11];
- сохранность данных за счет резервного копирования [12];
- доступность формализованных отчетов в распространенных форматах [13].

Таким образом, анализ предметной области подтверждает необходимость разработки единой информационной системы, объединяющей процессы ремонта, планового обслуживания и учета запасных частей в рамках одного программного решения.

1.2 Обзор программ-аналогов
В рамках исследования существующих решений для управления обслуживанием оборудования были рассмотрены распространенные классы программных продуктов, применяемые в сервисно-эксплуатационной деятельности: EAM/CMMS-платформы, helpdesk/ITSM-системы и универсальные low-code решения [14], [15].

1. CMMS/EAM-системы (класс решений для технического обслуживания)
Преимущества:
- развитые механизмы учета оборудования и регламентов ТО;
- встроенные метрики надежности и планирования ремонтов;
- поддержка истории обслуживания и анализа отказов.
Недостатки:
- высокая стоимость внедрения и владения;
- избыточная функциональность для небольших организаций;
- сложность адаптации интерфейса под локальные рабочие процессы.

2. ITSM/Helpdesk-платформы
Преимущества:
- удобная регистрация и маршрутизация заявок;
- контроль SLA и статусов обращения;
- интеграция с корпоративной коммуникационной средой.
Недостатки:
- ограниченная глубина учета планового ТО;
- недостаточная специализация под складской учет запчастей;
- необходимость кастомной доработки отчетных форм для задач эксплуатации.

3. Универсальные low-code/no-code платформы и табличные решения
Преимущества:
- быстрый запуск и гибкость настройки форм;
- низкий порог входа для пользователей;
- удобство первичного прототипирования.
Недостатки:
- сложности с обеспечением строгой ролевой модели и аудита;
- слабая масштабируемость при росте объема данных;
- ограниченные средства промышленного резервного копирования и восстановления.

Сравнительный анализ показывает, что готовые решения либо избыточны и экономически нецелесообразны для конкретной практико-ориентированной задачи, либо не обеспечивают необходимой связности между модулями «ремонт - ТО - склад - отчетность» [16], [17].

По результатам обзора обоснована разработка специализированного программного продукта BGSK1, который:
- ориентирован на конкретные процессы учета и сопровождения техники;
- реализует ролевую модель доступа, аудит и резервное копирование;
- предоставляет формализованную отчетность и инструменты оперативного контроля [18].

1.4 Разработка технического задания

Основание для разработки
Разработка программного продукта выполняется в рамках преддипломной практики по теме автоматизации процессов учета технического состояния оборудования, ремонта, планового обслуживания и складского учета запчастей.
Тема разработки: «Разработка информационной системы управления ремонтом и техническим обслуживанием оборудования».

Назначение разработки
Программный продукт BGSK1 предназначен для автоматизации работы сотрудников, отвечающих за эксплуатацию техники. Система обеспечивает:
- ведение реестра оборудования;
- регистрацию и сопровождение заявок на ремонт;
- планирование и контроль выполнения технического обслуживания;
- учет запасных частей;
- формирование аналитических и формализованных отчетов;
- резервное копирование данных и аудит действий пользователей.

Основные пользователи системы: администратор, аналитик, оператор.

Требования к программному продукту

Требования к функциональным характеристикам
Система должна обеспечивать выполнение следующих функций:
- авторизация пользователей по учетным данным с хранением паролей в виде хешей;
- разграничение доступа на основе ролей и прав;
- ведение справочника оборудования (добавление, редактирование, поиск, логическое удаление);
- создание и обработка заявок на ремонт с контролем статусов и приоритетов;
- назначение ответственных исполнителей по заявкам;
- ведение планов технического обслуживания и истории выполнения ТО;
- учет запасных частей, контроль минимальных остатков, фиксация расхода по заявкам;
- расчет ключевых показателей (открытые заявки, просроченное ТО, дефицит запчастей и др.);
- формирование отчетов по состоянию оборудования, SLA, ТО и закупкам;
- экспорт отчетов в форматы Excel и PDF, поддержка печати;
- ведение журнала аудита операций и истории отчетов;
- создание резервных копий базы данных.

Требования к организации входных и выходных данных
Входными данными являются:
- учетные данные пользователей (email, пароль);
- сведения об оборудовании (инвентарный номер, наименование, тип, местоположение, ответственный, статус);
- данные заявок на ремонт (описание неисправности, приоритет, исполнитель, статус);
- данные планов ТО (тип обслуживания, периодичность, плановая дата);
- данные по складу запчастей (номенклатура, артикул, текущий остаток, минимальный остаток);
- параметры формирования отчетов (период, вид отчета, формат экспорта).

Выходными данными являются:
- списки и карточки оборудования;
- реестр заявок и сведения о ходе их исполнения;
- перечень просроченных работ по ТО;
- отчеты по расходу запчастей и потребности в закупке;
- сводные KPI-показатели;
- файлы отчетов в форматах Excel/PDF;
- записи журналов аудита и истории формируемых отчетов;
- информация о созданных резервных копиях.

Требования к временным характеристикам
- отклик интерфейса при типовых действиях пользователя - не более 2-3 секунд;
- открытие основных форм системы - не более 5 секунд;
- выполнение операций добавления/обновления записи в БД - не более 3 секунд;
- формирование отчетов среднего объема - до 30 секунд.

Требования к пользовательскому интерфейсу
- графический интерфейс в виде многооконного настольного приложения;
- наличие формы авторизации;
- главное меню с доступом к модулям: оборудование, заявки, ТО, склад запчастей, отчеты, бэкапы, пользователи, администрирование прав;
- табличное представление данных с возможностью сортировки и фильтрации;
- формы создания и редактирования записей;
- отображение ключевых показателей на панели мониторинга;
- понятные уведомления об ошибках и результатах операций.

Требования к надежности
Программный продукт должен обеспечивать:
- защиту данных от несанкционированного доступа;
- хранение паролей в виде криптографических хешей;
- контроль корректности вводимых данных;
- ограничение способов ввода значений в интерфейсе:
  - для фиксированных наборов значений должны использоваться только выпадающие списки (например: статус заявки, приоритет заявки, выбор оборудования);
  - ручной ввод произвольного значения в таких полях не допускается;
- ограничение диапазонов числового ввода:
  - поле периодичности ТО - только целое число в пределах 1-365;
  - поля количества и минимального остатка запчастей - только неотрицательные целые значения;
  - ввод дробных, буквенных и специальных символов в числовые поля не допускается;
- контроль длины и заполненности текстовых полей:
  - обязательные поля (логин, описание неисправности, наименование оборудования и др.) не могут быть пустыми;
  - значения перед сохранением должны проходить нормализацию (удаление лишних пробелов по краям);
  - длина строковых полей должна ограничиваться в соответствии со структурой БД;
- форматные ограничения (маски) для критичных реквизитов:
  - поля, требующие фиксированного формата, должны проверяться по шаблону до записи;
  - при несоответствии формату операция сохранения блокируется;
- использование чекбоксов для логических параметров:
  - активность плана ТО;
  - включение/отключение фильтров «только просроченные» и «только дефицитные»;
- контроль операций редактирования и удаления:
  - операции «Изменить», «Удалить», «Закрыть», «Отметить» разрешены только при выборе существующей записи в таблице;
  - при отсутствии выбранной записи система должна выдавать предупреждение и не выполнять действие;
- обработку ошибок ввода и системных исключений:
  - для каждого некорректного ввода выводится понятное диагностическое сообщение;
  - приложение не должно завершаться аварийно при ошибке ввода пользователя;
- выполнение операций записи в БД только через параметризованные запросы с защитой от SQL-инъекций;
- журналирование изменений (аудит CRUD-операций);
- устойчивую работу при некорректных действиях пользователя;
- возможность резервного копирования и восстановления данных.

Условия эксплуатации
Для нормальной эксплуатации системы необходимы:
- персональный компьютер пользователя;
- установленная ОС семейства Windows;
- доступ к серверу СУБД;
- локальная сеть или иное стабильное соединение с сервером БД;
- наличие прав на запуск приложения и доступ к рабочим каталогам экспорта/бэкапов.

Требования к составу и параметрам программных средств
- процессор: от 2 ядер, частота от 2.0 ГГц;
- оперативная память: не менее 4 ГБ (рекомендуется 8 ГБ);
- свободное место на диске: не менее 2 ГБ для приложения и отчетов;
- операционная система: Windows 10 и выше;
- платформа: .NET Framework 4.8;
- СУБД: Microsoft SQL Server (Express/Standard).

Требования к информационной и программной совместимости
- хранение данных должно осуществляться в реляционной БД MS SQL Server;
- система должна поддерживать экспорт отчетов в распространенные офисные форматы (Excel, PDF);
- структура БД должна поддерживать расширение предметной области без полной переработки архитектуры.

Требования к программной документации
Документация должна включать:
- руководство пользователя;
- руководство программиста (структура проекта, модули, порядок доработки);
- описание структуры базы данных;
- инструкции по установке и первичной настройке.

Этапы разработки программного продукта
- анализ предметной области и требований;
- проектирование структуры данных и архитектуры модулей;
- реализация основных модулей системы;
- настройка механизмов безопасности и разграничения прав;
- реализация отчетности, экспорта и печати;
- внедрение резервного копирования и аудита;
- тестирование и устранение выявленных дефектов;
- подготовка эксплуатационной документации.

2 Разработка программного продукта

2.1 Разработка архитектуры программной системы
На основе сформированного технического задания и набора требований к функциональным характеристикам была разработана архитектура программной системы BGSK1. Разрабатываемый программный продукт представляет собой настольное приложение на платформе .NET Framework 4.8 с графическим интерфейсом Windows Forms и централизованным хранением данных в СУБД Microsoft SQL Server.

Рисунок 2.1.2 - Архитектура взаимодействия уровней (UI - Service - DB)

Программная система имеет трехуровневую архитектуру:
- уровень представления (формы и элементы управления);
- уровень прикладной логики (сервисы предметной области);
- уровень хранения данных (таблицы, ограничения и процедуры работы с БД).

Модуль «Авторизация» реализует аутентификацию пользователей, верификацию паролей и первичную загрузку пользовательского контекста (идентификатор, роль, ФИО). Также модуль обеспечивает регистрацию попыток входа и обработку ошибок аутентификации.

Модуль «Техника» предназначен для ведения реестра оборудования. Модуль включает функции добавления, редактирования и поиска карточек оборудования по инвентарному номеру, наименованию, типу, местоположению и ответственному лицу.

Модуль «Заявки на ремонт» обеспечивает создание заявок, назначение приоритета и исполнителя, изменение статусов (новая, в работе, ожидание, завершена), а также контроль жизненного цикла заявки до момента закрытия.

Модуль «Плановое ТО» реализует планирование регламентных работ, хранение периодичности обслуживания, контроль следующей даты ТО, фиксацию факта выполнения работ и перенос следующего планового срока.

Модуль «Склад запчастей» реализует количественный учет номенклатуры запчастей, контроль минимальных остатков, операции пополнения и списания, а также фильтрацию позиций с дефицитом.

Модуль «Отчеты» предназначен для формирования аналитических и формализованных отчетов по ключевым направлениям: открытые заявки, просроченное ТО, дефицит запчастей, нагрузка исполнителей. Модуль включает экспорт в форматы CSV, HTML, XLS, DOC и PDF, а также вывод отчетных данных на печать.

Модуль «Журнал отчетов» обеспечивает хранение истории сформированных документов и пути к файлам выгрузки.

Модуль «Аудит» реализует просмотр журналов действий пользователей и изменений данных, включая дату/время операции, пользователя, объект изменения и тип действия.

Модуль «Резервные копии» обеспечивает создание, хранение и восстановление резервных копий базы данных, что повышает отказоустойчивость и обеспечивает восстановление после сбоев.

Таким образом, архитектурное решение соответствует требованиям технического задания и обеспечивает расширяемость, модульность и сопровождение программного продукта.

2.4.2 Обработка ввода данных
Обработка ввода данных в программном продукте реализована в обработчиках событий интерфейса и в сервисных методах. На стороне формы выполняется первичная валидация (заполненность полей, корректность выбора строки, допустимость значений), на стороне сервиса - параметризация SQL-запросов, запись в журнал аудита и обработка исключений.

Фрагмент 1 - обработка ввода данных при авторизации пользователя (`BtnLogin_Click`)
В обработчике извлекаются логин и пароль из полей ввода, выполняется попытка аутентификации и обрабатывается результат:

var email = _txtEmail.Text.Trim();
var password = _txtPassword.Text;
var ip = "127.0.0.1";

if (AuthService.TryLogin(email, password, ip, out var error))
{
    SaveLastLogin(email);
    DialogResult = DialogResult.OK;
    Close();
    return;
}

_lblError.Text = error;

Назначение обработки:
- защита от ввода с лишними пробелами за счет `Trim`;
- централизованная проверка учетных данных через сервис;
- вывод текстового сообщения об ошибке без аварийного завершения приложения.

Фрагмент 2 - обработка ввода данных при создании заявки на ремонт (`BtnCreateRequest_Click`)
Перед созданием заявки выполняется проверка обязательных полей:

if (_cmbEquipmentForRequest.SelectedValue == null || string.IsNullOrWhiteSpace(_txtProblem.Text))
{
    MessageBox.Show("Выберите технику и заполните описание неисправности.", "Валидация", MessageBoxButtons.OK, MessageBoxIcon.Warning);
    return;
}

RunAction(() =>
{
    RepairRequestService.CreateRequest(Convert.ToInt32(_cmbEquipmentForRequest.SelectedValue), _txtProblem.Text.Trim(), _cmbPriority.Text, _txtAssigned.Text.Trim());
    ReloadAll();
});

Назначение обработки:
- запрет создания заявки без выбранного оборудования и описания неисправности;
- нормализация строковых полей перед записью (`Trim`);
- безопасный запуск операции через `RunAction` с обработкой исключений;
- автоматическое обновление интерфейса после записи данных в БД.

Фрагмент 3 - обработка ввода данных при списании запчастей (`WriteOffPart`)
Проверка и изменение количества выполняются в сервисе с защитой от отрицательных остатков:

UPDATE dbo.SpareParts
SET QuantityInStock = CASE WHEN QuantityInStock >= @Quantity THEN QuantityInStock - @Quantity ELSE 0 END,
    LastUpdated = SYSUTCDATETIME()
WHERE Id = @PartId;

Db.ExecuteNonQuery(sql, new SqlParameter("@PartId", partId), new SqlParameter("@Quantity", quantity));

Назначение обработки:
- исключение некорректного результата (отрицательного остатка на складе);
- защита от SQL-инъекций за счет параметризованного запроса;
- фиксация изменения в журнале аудита через `AuditService.LogChange(...)`.

Таким образом, обработка ввода данных реализована по принципу двухуровневого контроля: проверка на уровне пользовательской формы и защищенная запись на уровне сервиса доступа к данным.

2.4.3 Организация хранения данных
Организация хранения данных реализована на базе MS SQL Server с централизованной схемой таблиц и ограничений целостности.

Основные принципы хранения данных:
- разделение данных на предметные и служебные сущности;
- использование первичных и внешних ключей;
- хранение временных меток создания и изменения записей;
- применение логического удаления для выбранных таблиц;
- хранение истории действий и отчетных документов.

Схема инициализации БД выполняется скриптом `01_create_schema.sql`, который:
- создает базу данных и таблицы предметной области;
- создает таблицы безопасности, аудита, отчетности и бэкапов;
- добавляет ограничения уникальности и внешние ключи;
- формирует стартовые роли и набор прав доступа;
- добавляет тестовые записи для демонстрации и отладки.

Доступ к данным организован через инфраструктурный слой `Db`, который обеспечивает выполнение:
- команд выборки (`SELECT`) с возвратом `DataTable`;
- команд изменения (`INSERT`, `UPDATE`, `DELETE`);
- скалярных запросов для получения одиночных значений.

- триггер аудита `trg_DataRecords_Audit` для дополнительной фиксации изменений в `DataRecords`.

Таким образом, разработанная система хранения данных обеспечивает целостность информации, контроль изменений, восстановление после сбоев и выполнение требований по отчетности, безопасности и сопровождению программного продукта.

- для просмотра Excel-отчетов: Microsoft Excel или совместимое приложение (опционально);
- для просмотра PDF-отчетов: программа просмотра PDF (опционально).
Характеристики программы
Программа состоит из набора модулей (сборка BGSK1, исполняемый файл BGSK1.exe) и вспомогательных компонентов:
- модуль «Окно авторизации» (класс LoginForm) — аутентификация пользователя и передача управления главному окну;
- модуль «Главное меню» (класс MainMenuForm) — панель мониторинга, боковая навигация и открытие модулей в рабочей области;
- модуль «Техника» (класс EquipmentForm и связанные формы создания/редактирования) — просмотр, добавление, изменение и логическое удаление записей оборудования;
- модуль «Заявки на ремонт» (класс RequestsForm и связанные формы) — создание и сопровождение заявок, изменение статусов, назначение исполнителей;
- модуль «Плановое ТО» (класс MaintenanceForm и связанные формы) — ведение планов обслуживания и фиксация выполнения;
- модуль «Склад запчастей» (класс PartsForm и связанные формы) — ведение складских позиций, списание, контроль низкого остатка;
- модуль «Отчетный центр» (класс ReportsCenterForm) — формирование предметных выборок, экспорт в Excel/PDF, печать, просмотр журнала сформированных отчетов;
- модуль «Бэкапы» (класс BackupForm) — создание и восстановление резервной копии базы данных;
- модуль «Пользователи» (класс UserManagementForm) — администрирование учетных записей (при наличии прав);
- модуль «Администрирование прав» (класс AdminPermissionsForm) — настройка прав ролей (при наличии прав);
- инфраструктурный слой доступа к данным (класс Db, скрипты SQL) — выполнение запросов к СУБД;
- сервисный слой предметной области (классы каталога Services) — реализация бизнес-операций и валидации.
Обращение к программе
Программа запускается с помощью исполняемого файла BGSK1.exe, расположенного в каталоге сборки (например, BGSK1\bin\Debug или BGSK1\bin\Release после компиляции проекта). Запуск производится двойным щелчком мыши по файлу либо из среды разработки Microsoft Visual Studio.
Для корректной работы приложения необходимо, чтобы серверная часть базы данных (MS SQL Server) была запущена и доступна по параметрам, указанным в конфигурационном файле App.config (строки подключения MasterConnection и AppConnection).
При запуске программы выполняется инициализация базы данных (создание при отсутствии, применение схемы), затем отображается окно авторизации. В случае успешной авторизации открывается главное меню (MainMenuForm), предоставляющее доступ к модулям через боковую панель навигации.
При некорректных данных авторизации, ошибке подключения к серверу или ошибке инициализации базы данных выводится соответствующее сообщение.

            Application.SetCompatibleTextRenderingDefault(false);

                    return;
                }
            }

            RolePermissionService.LoadCurrentRolePermissions();
            Application.Run(new MainMenuForm());
        }
    }
}

using System;
using System.Configuration;
using System.Data;
using System.Data.SqlClient;

namespace BGSK1.Infrastructure
{
    internal static class Db
    {
        public static string MasterConnectionString =>
            ConfigurationManager.ConnectionStrings["MasterConnection"].ConnectionString;

        public static string AppConnectionString =>
            ConfigurationManager.ConnectionStrings["AppConnection"].ConnectionString;

        public static object ExecuteScalar(string sql, params SqlParameter[] parameters)
        {
            using (var connection = new SqlConnection(AppConnectionString))
            using (var command = new SqlCommand(sql, connection))
            {
                if (parameters != null)
                {
                    command.Parameters.AddRange(parameters);
                }

                connection.Open();
                return command.ExecuteScalar();
            }
        }

        public static int ExecuteNonQuery(string sql, params SqlParameter[] parameters)
        {
            using (var connection = new SqlConnection(AppConnectionString))
            using (var command = new SqlCommand(sql, connection))
            {
                if (parameters != null)
                {
                    command.Parameters.AddRange(parameters);
                }

                connection.Open();
                return command.ExecuteNonQuery();
            }
        }

        public static DataTable ExecuteDataTable(string sql, params SqlParameter[] parameters)
        {
            using (var connection = new SqlConnection(AppConnectionString))
            using (var command = new SqlCommand(sql, connection))
            {
                if (parameters != null)
                {
                    command.Parameters.AddRange(parameters);
                }

                using (var adapter = new SqlDataAdapter(command))
                {
                    var table = new DataTable();
                    adapter.Fill(table);
                    return table;
                }
            }
        }
    }
}

                Left = 24,

                Width = 360,

                Font = new Font("Segoe UI Semibold", 14f, FontStyle.Bold),

            var lblPassword = ThemeHelper.FormFieldLabel("Пароль:", 24, 114, 120, ThemeHelper.MutedText);
            _txtPassword = new TextBox { Left = 24, Top = 136, Width = 370, PasswordChar = '*', BorderStyle = BorderStyle.FixedSingle };

            _btnLogin = new Button

                BackColor = ThemeHelper.Primary,
                ForeColor = Color.White
            };

            _btnLogin.Click += BtnLogin_Click;

            _lblError = new Label { Left = 24, Top = 218, Width = 380, Height = 26, ForeColor = Color.Firebrick };

            card.Controls.Add(lblTitle);
            card.Controls.Add(lblEmail);
            card.Controls.Add(_txtEmail);
            card.Controls.Add(lblPassword);
            card.Controls.Add(_txtPassword);
            card.Controls.Add(_btnLogin);
            card.Controls.Add(_lblError);

            Controls.Add(card);
            Shown += (s, e) => RestoreLastLogin();
        }

        private void BtnLogin_Click(object sender, EventArgs e)
        {
            var email = _txtEmail.Text.Trim();
            var password = _txtPassword.Text;
            var ip = "127.0.0.1";

            if (AuthService.TryLogin(email, password, ip, out var error))
            {
                SaveLastLogin(email);
                DialogResult = DialogResult.OK;
                Close();
                return;
            }

            _lblError.Text = error;
        }

        private void RestoreLastLogin()
        {
            try
            {
                if (File.Exists(LastLoginFilePath))
                {
                    _txtEmail.Text = File.ReadAllText(LastLoginFilePath).Trim();
                }
            }
            catch
            {
                // Игнорируем ошибки доступа: это вспомогательная функция.
            }

            _txtPassword.Text = string.Empty;
        }

        private static void SaveLastLogin(string login)
        {
            try
            {
                File.WriteAllText(LastLoginFilePath, login ?? string.Empty);
            }
            catch
            {
                // Игнорируем ошибки записи: вход в систему не должен из-за этого падать.
            }
        }
    }
